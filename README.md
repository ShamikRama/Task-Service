# Task Service

Сервис для управления задачами с HTTP API на Go.

## Требования

- Go `1.23+`
- Docker и Docker Compose

## Быстрый запуск через Docker Compose

```bash
docker compose up --build
```

После запуска сервис будет доступен по адресу `http://localhost:8080`.

Если `postgres` уже запускался ранее со старой схемой, пересоздай volume:

```bash
docker compose down -v
docker compose up --build
```

Причина в том, что SQL-файл из `migrations/0001_create_tasks.up.sql` монтируется в `docker-entrypoint-initdb.d` и применяется только при инициализации пустого data volume.

## API

Базовый префикс API:

```text
/api/v1
```

Основные маршруты:

- `POST /api/v1/tasks`
- `GET /api/v1/tasks`
- `GET /api/v1/tasks/{id}`
- `PUT /api/v1/tasks/{id}`
- `DELETE /api/v1/tasks/{id}`
- `POST /api/v1/templates/create`
- `GET /api/v1/templates`
- `GET /api/v1/templates/{id}`
- `PUT /api/v1/templates/{id}`
- `DELETE /api/v1/templates/{id}`

### Обоснование решения

## Суть подхода — разделить описание правила и факт выполнения

Я вынес периодичность в отдельную сущность `template` (шаблон).

- Шаблон хранит правило: как и когда должны появляться задачи.
- Задачи — это материализованные экземпляры правила на конкретные даты.
- Планировщик регулярно догенерирует задачи на горизонт вперёд, чтобы не создавать слишком много записей в БД заранее.

Зачем:

- правило настраивается один раз, дальше задачи создаются автоматически.
- шаблон можно менять/деактивировать, а у конкретной задачи при необходимости можно переопределить связь с шаблоном и дату.
- генерация в пределах горизонта снижает избыточный рост таблицы задач, воркер нужен именно для случая, когда end_date не задан или далеко в будущем.

## Замечания

Во втором скриншоте было поле `scheduled_at` (срок выполнения), но в модели и в таблице БД его не было.  
Я добавил это поле как `scheduled_date`, чтобы задача имела явную плановую дату.
